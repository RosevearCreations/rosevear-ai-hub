### Implemented controls

1. `master_acceptance353.py` requires *two distinct* original-host boot observations, each individually signed with the independent QL-461 host witness key; verifies their chronology, original-host identity, manifest scope, valid Task Scheduler observations, and fresh post-boot receipt. A **separate** reviewer-key signature ties both exact receipt digests to the same original host, manifest and boot IDs. The reviewer key must differ from both the owner enrollment key and the host witness key. A valid output is **SIGNED_TWO_BOOT_SEQUENCE_AND_REVIEWER_ASSERTION**, not proof that Windows autonomously restarted or that an independent observer physically witnessed it. Windows Task Scheduler Operational event logs, true post-reboot startup, recovery and continuous 24-hour evidence remain separate operational gates.
2. Comms audit linkage verifies a Comms Ed25519-signed `ACKNOWLEDGED` owner-level receipt **and** an additional Comms-signed audit record, bound to the exact message, event digest, owner-allowlisted audit identifier, outcome, event chronology and full audit digest. The validated signed receipts must also be present in the original-host protected outbox. A signature shows **Comms' audited assertion**, not independent human-read proof unless the underlying Comms source session and actor trace are separately validated.
3. Opt-in original-host `--enqueue-pilot --pilot-audience ai-data-platform` or `rosevear-comms-hub` takes a **fresh real local SCM event** from the hash-checked QL-460 journal, signs a v1.1 read-only `master.health` event with the active enrolled Hub Ed25519 key and queues exactly one target. An inactive/unknown target, missing valid signer or stale source fails closed. It never opens a network connection or starts a Master. To perform a *real* pilot, separately run the existing `--deliver <messageId>`, using independently enrolled mTLS CA/client certificate/key and pinned peer leaf, a deployed recipient event sink, a fresh signed peer `RECEIVED` ACK and protected outbox custody. Source runs here cannot perform a live test on the physical PC.
4. Rotation dashboard uses the owner-signed QL-461 registry (Ed25519 key pins, effective/expiry and revocation times), enforces the existing one-day overlap bound, flags absent/expired/soon-to-expire service keys and future pre-enrolled generations. It **never automatically issues, rotates, revokes or exposes private keys**. Activation of a next generation requires an independently owner-signed updated registry, a locally reconfigured signing key ID, deliberate private-key provisioning, peer enrollment and a separately witnessed pilot.
5. Owner-only, no-cache `GET /api/v1/system/server-shell-353` and corresponding futuristic Server Shell panel show separate evidence for the reboot ceremony, each Master peer's historical transport ACK, Comms audit link, and key expiry. No endpoint lets the UI send, ACK, reboot, start/stop services, modify keys or activate a physical device.
